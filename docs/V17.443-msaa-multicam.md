# CSE WARP V17.443 — MSAA, resolve GPU et multi-caméras

## Objectif
Sur la scène **complexe sportif avec piscine**, la campagne précédente (51 essais, 17 variantes) a montré que le temps d'image variait fortement avec la résolution et le MSAA, tandis que les ombres GPU et le détail PBR avaient peu d'impact sur la caméra initiale. Il faut maintenant distinguer **rasterisation/remplissage**, **résolution multi-échantillon**, **copie vers le staging GPU**, **attente CPU du staging**, et comparer le tout sur **chaque caméra enregistrée**, notamment piscine et verrières.

## Ce qui est nouveau dans la branche
- D3D11 : timestamp GPU placé **juste après `ResolveSubresource`**, avant `CopyResource`; le même point marque la fin d'un chemin sans resolve à MSAA 1×.
- Les résultats par caméra publient `gpuDrawMs`, `gpuResolveMs`, `gpuStagingCopyMs`, `gpuTransferMs`, `gpuTotalMs`, `cpuMapWaitMs`, `cpuPixelConvertMs`.
- `gpuTransferSplitValid` distingue un horodatage réel d'un zéro non mesuré; test de cohérence : `gpuResolveMs + gpuStagingCopyMs ≈ gpuTransferMs`. Les horodatages sont facultatifs pour le rendu classique, mais **obligatoires pour ce benchmark**.
- **Aucun changement de shaders, de géométrie, de textures, de matériaux, d'ombres ou de qualité d'image.** Pas de mode qualité dégradée pour « optimiser » artificiellement.
- Le benchmark multi-caméras relance l'exécutable avec les mêmes scènes, la même heure (12 h), la même résolution native (sauf essais explicitement marqués), les mêmes réglages autres que le seul facteur étudié.

## Configurations de diagnostic
MSAA 1×/2×/4×/8× avec lecture GPU profondeur 1 ; MSAA 2×/4× avec profondeur 3 ; MSAA 2× à 960×540 et 1920×1080. **Chaque cas utilise toutes les caméras prédéfinies**, trois répétitions de 24 images par défaut, avec ordre de passage alterné.

Référence par caméra : `MSAA2_DEPTH1`, 1366×768, anisotropie 8×, LOD 100 % activé, culling activé. L'analyse ne compare jamais directement deux caméras différentes pour attribuer le coût d'un réglage.

## Interprétation
- Si `gpuDrawMs` augmente fortement avec MSAA et la résolution alors que `gpuResolveMs` reste faible, le goulet est vraisemblablement dans le **rendu multisample** (couverture, remplissage, bande passante), pas dans la simple opération `ResolveSubresource`.
- Si `gpuResolveMs` s'envole à 4×/8×, nous aurons identifié un coût réel de la résolution MSAA.
- Si `gpuStagingCopyMs` ou `cpuMapWaitMs` dominent, agir sur le **chemin de lecture** plutôt que sur les matériaux. Le 3-buffering est mesuré en `streamMeanMs` / `streamFps`, pas uniquement en latence d'image.
- Si certaines vues vitrées coûtent beaucoup plus que d'autres, préparer ensuite un A/B ciblé sur les surfaces transparentes et l'overdraw. Ce test **n'est pas encore intégré** : il exige un traitement distinct de la transparence.
- Les versions MSAA peuvent négocier un échantillonnage inférieur selon le GPU ; ces essais relèvent une **qualité demandée** et un coût observé, pas encore le nombre réellement négocié par D3D11.
- Les FPS mesurés sont estimés via rendu + lecture GPU ; **pas** le FPS de la fenêtre Qt en exploration.

## Exécuter sur le PC Intel HD 620
Fermer intégralement CSE WARP et le mode Exploration, alimenter l'ordinateur sur secteur, conserver les mêmes conditions thermiques. Télécharger la branche **V17.443 MSAA-MULTICAM-DIAGNOSTIC** lorsque son workflow GitHub Actions est vert, extraire l'archive dans un dossier neuf, puis sous PowerShell :

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\bench_v443_msaa_multicam.ps1 -RuntimeRoot . -Passes 3 -Frames 24
python .\tools\analyze_msaa_multicam_v443.py .\benchmarks-msaa-multicam
```

Les mesures iront dans `benchmarks-msaa-multicam` ; fournir son ZIP complet pour analyse. Rapports `msaa_multicam_report.md`, `msaa_multicam_summary.csv`, `msaa_multicam_summary.json` et `msaa_multicam_raw.csv`.

Le paramètre `-SoftwareWarp` force le rendu logiciel **Microsoft WARP**, à utiliser uniquement pour un contrôle logiciel distinct du véritable GPU. La compilation sur GitHub Actions n'est qu'une validation fonctionnelle ; **les résultats de performances utiles doivent venir du PC HD 620**.

La branche de benchmark reste distincte de la V17.443 livrée. Ne pas fusionner une optimisation sans examen d'une différence d'image et mesure sur matériel.
